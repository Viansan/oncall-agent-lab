# On-call Agent Lab：从检索到工具调用 Agent 的产品实验

> 用同一组合成运行手册，比较关键词检索、轻量语义检索和工具调用 Agent：每次升级解决什么问题，又增加多少成本、延迟与失控风险。

这是一个面向 AI 产品设计的可运行实验，不是真实生产系统，也不提供真实故障处置建议。仓库中的服务、运行手册、命令、故障问题和评测标签均为本项目重新编写的虚构内容。

## 用户问题

值守人员遇到故障时，真正需要的不是“再多一个聊天框”，而是在较短时间内完成三件事：

1. 找到与当前现象最相关的运行手册；
2. 看清系统依据了什么，而不是只得到一个无法追溯的答案；
3. 当知识库没有覆盖问题时及时停止，避免把猜测当成处置建议。

这个实验把同一个问题拆成三阶段，只有上一阶段暴露出稳定缺口时才增加复杂度。

## 三阶段演进

### 1. 关键词检索：先解决“找得到”

`GET /v1/search?q=...`

使用依赖标准库实现的 BM25-style 词面排序。它的优势是没有外部模型成本、响应快、命中原因清楚；缺点是用户换一种说法时容易漏召回。

例如运行手册写的是“请求响应时间升高”，用户说“保存时一直转圈”，词面检索未必能把两者联系起来。

### 2. 轻量语义检索：解决常见同义表达

`GET /v2/search?q=...`

把领域内的同义说法映射到透明的概念向量，再结合少量词面分数排序。它可以离线运行，也能展示“为什么命中”。

这里刻意没有把它包装成通用 Embedding 模型：它适合验证产品假设，但依赖人工维护的领域词典，遇到词典外问题不会自然泛化。生产化时可以在保留同一评测集的前提下替换为向量模型。

### 3. 工具调用 Agent：解决“跨文档选择与组织答案”

`POST /v3/chat`

Agent 根据问题选择一到两份手册，调用 `read_runbook(document_id)`，展示调用与返回轨迹，再组织带文档 ID 的处置建议。

工具被限定为：

- 只接受预先加载的文档 ID；
- 不能列目录、拼接文件路径或读取任意文件；
- 不能写文件、执行命令或改变外部状态；
- 知识库不覆盖时不调用工具，直接转人工。

默认使用确定性的离线 Planner，保证评测可复现且没有外部模型调用。另提供可选的通用 chat-completions Live 模式，用于观察真实模型的选文档、引用、延迟和 token 使用；Live 结果不计入默认基准。

## 为什么要这样升级

| 阶段 | 解决的主要缺口 | 新增代价 | 可解释性 | 主要失败边界 |
| --- | --- | --- | --- | --- |
| 关键词检索 | 精确词命中与快速定位 | 无外部模型成本；本地计算 | 高，可展示词面命中 | 同义改写、跨表达漏召回 |
| 概念向量语义检索 | 领域内的同义表达 | 需要维护概念与别名 | 较高，可展示命中概念 | 词典外问题、概念歧义、领域迁移 |
| 工具调用 Agent | 跨文档选择、读取和回答组织 | Live 模式增加模型费用和网络延迟 | 工具轨迹可见，但模型推理不等于事实 | 选错文档、漏读文档、无依据生成、工具轮次耗尽 |

复杂度不是能力证明。只有统一评测表明上一阶段确实无法覆盖目标问题，升级才有价值。

## 统一评测设计

所有方法使用同一组合成运行手册与同一问题集，避免为某一阶段单独挑题。

问题集包含 13 个问题：

- 精确表达：验证基础词面命中；
- 同义改写：验证用户换一种说法后的召回；
- 跨服务问题：验证是否需要读取两份手册；
- 知识边界：验证系统是否在不相关问题前停止。

指标定义：

- `Hit@3`：前三个检索结果是否包含任一目标文档；
- `MRR`：第一个正确文档的倒数排名；
- 文档召回：Agent 实际读取的目标文档比例；
- 边界准确率：该回答时回答、该停止时停止；
- 引用率：回答是否标注所有应使用的文档 ID；
- 中位延迟：本机单进程离线测量，只用于同环境相对比较。

在 2026-08-20 的本地离线运行中：

| 方法 | 评测范围 | 核心结果 | 中位延迟快照 |
| --- | --- | --- | --- |
| 关键词 BM25-style | 11 个可回答问题 | Hit@3 `0.909`，MRR `0.864` | `0.08 ms` |
| 概念向量语义检索 | 11 个可回答问题 | Hit@3 `1.000`，MRR `1.000` | `0.14 ms` |
| 离线工具 Agent | 全部 13 个问题 | 文档召回、边界准确率、引用率均为 `1.000` | `0.13 ms` |

这些数字只说明当前小型合成数据集中的行为，不代表生产准确率。运行环境和微小语料变化都会影响延迟与排序；完整逐题结果可用 `--json` 查看。

```bash
python -m evals.run_eval
python -m evals.run_eval --json
```

## 关键产品判断

### 工具轨迹不等于答案正确

界面把工具调用、工具返回和最终回答分开显示。它能证明“系统读了什么”，但不能证明选文档正确、引用完整或建议安全，因此仍需用评测标签验收最终结果。

### 拒答是正常结果

“差旅报销”“办公室温度”等问题不在知识库范围内。离线 Agent 不会为了保持对话流畅而拼凑答案，而是停止工具调用、说明信息不足并转人工。

### 默认离线，Live 明示成本

离线模式零外部模型调用，适合演示、回归测试和 CI。Live 模式会产生网络延迟和模型费用，具体成本取决于所接服务，因此仓库只记录调用次数和 token 使用，不写死价格。

## 数据与安全边界

- 五份运行手册位于 `data/runbooks/`，全部是虚构服务和合成文本；
- 示例命令使用不存在的 `labctl`，不得用于真实生产环境；
- Live 模式的 Key 只从环境变量读取，`.env` 已被忽略；
- Live 模式还需显式设置 `ENABLE_LIVE_MODE=true`，避免公开部署后意外产生外部调用费用；
- Agent 工具按逻辑 ID 读取白名单文档，拒绝任意路径；
- 前端用文本节点展示返回内容，不把模型回答直接注入 HTML；
- 离线模式不会把用户问题发送到外部服务，也不持久化对话；
- Live 模式会把用户问题、系统指令以及允许读取的手册片段和工具结果发送给所配置的模型服务商。应用本身不持久化这些对话，但服务商可能按其政策处理或留存，因此不要输入真实故障信息、凭证或其他敏感数据。

## 我的职责与 AI 的参与

**我的职责**

- 定义用户问题、三阶段演进逻辑和每次升级的通过条件；
- 设计统一问题集、指标、知识边界与工具权限；
- 决定用合成数据替代任何来源不清晰的题目和运行手册；
- 对可运行性、评测结果、文档表达和公开风险做最终验收。

**AI coding assistant 的参与**

- 在上述约束下辅助实现通用代码、测试和界面；
- 协助整理文档结构和检查遗漏；
- 不作为需求来源，也不替代结果验收。

这里不把“AI 生成了代码”包装成个人手写能力。这个项目主要展示的是：如何把一个 AI 产品问题拆成可运行机制，并用统一证据判断复杂度是否值得。

## 运行方式

需要 Python 3.10+。

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
python -m pytest
python -m evals.run_eval
uvicorn main:app --reload
```

浏览器打开 `http://127.0.0.1:8000`。也可以执行：

```bash
./start.sh
```

### 可选 Live 模式

只有需要验证真实函数调用时才配置 Live 模式：

```bash
cp .env.example .env
```

填写通用兼容接口配置并将 `ENABLE_LIVE_MODE` 改为 `true` 后，把 `.env` 中变量导入当前 shell，再在页面选择 Live 模式。仓库不会提供或内置任何 API Key，也不建议在无鉴权的公开部署中开启 Live 模式。

## 已知限制与下一步

- 当前语义层是透明的领域基线，不是通用向量模型；
- 合成问题集规模小，满分不能外推到真实值守场景；
- 离线 Agent 的回答模板固定，主要用于验证选文档、工具边界和引用；
- Live 模式尚未建立跨模型稳定性、提示注入和成本基准；
- 真实生产系统还需要身份鉴权、审计、数据分级、变更审批和人工接管。

下一步应先扩大盲测问题集，并加入“检索到了错误文档”“手册之间冲突”“文档包含恶意指令”等失败样本，再决定是否引入真正的 Embedding、重排模型或更复杂的 Agent。
